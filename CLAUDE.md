## What this is

A ComfyUI custom node pack whose real product is a **frontend viewer panel**: a floating, dockable image/video/3D viewer with tabs, history, comparison, playback, a file browser, drawing tools and a 3D previz tool. Python here is the thin half — four nodes and a set of `/imageviewer/*` HTTP routes; the JavaScript in `js/` is the thick half.

`__init__.py` exports the nodes, imports `viewer_api` (which registers the routes as a side effect of import), and sets `WEB_DIRECTORY = "js"`, which is how ComfyUI serves the frontend from `/extensions/ComfyUI-ImageViewer/`.

The repository root holds only what the ComfyUI custom node layout needs there (`__init__.py`, `pyproject.toml`, `requirements.txt`, `js/`) plus `docs/`, `tests/` and `vendor/`. Every other Python module is in the `src/` package (`src/nodes.py`, `src/viewer_api.py`, ...) and imports its siblings relatively (`from . import timeline_io`); a module named below without a folder is in `src/`.

## Running and testing

Nothing to build: the JS is plain ES modules served as-is, and Python needs no compilation step. There is a test suite in `tests/` (`D:/AI/agentY/.venv/Scripts/python.exe -m unittest discover -s tests` and `node --test tests/*.mjs` - node's own discovery finds nothing, the files are named `test_*.mjs`); the tests that need PyAV (`test_timeline_media_routes.py`) are skipped there and run with ComfyUI's interpreter, `D:/ai/comfyui/.venv/Scripts/python.exe -m unittest discover -s tests -p "test_timeline_media_routes.py"`. Browser tests serve `tests/harness/*.html` (the real viewer js, ComfyUI stubbed) through `tests/harness/server.mjs` with Playwright. Beyond those, two things stand in for a test runner, and both are worth rebuilding when you change anything non-trivial.

Use ComfyUI's own interpreter, never a bare `python`:

```bash
D:/ai/comfyui/.venv/Scripts/python.exe -s <script>      # -s: ignore user site-packages
node --check js/imageViewer_model3d.js                  # the only "lint" the JS has
D:/ai/comfyui/.venv/Scripts/python.exe -m py_compile src/viewer_api.py
```

**Python-side checks** run the real modules with ComfyUI stubbed, in a scratch directory (not in the repo). The pattern each such script follows:

```python
sys.path.insert(0, r"D:\ai\comfyui")          # for folder_paths and comfy_extras
import folder_paths
folder_paths.set_output_directory(tmp); folder_paths.set_input_directory(...)   # scratch dirs
sys.modules["server"] = <module exposing PromptServer.instance.app + send_sync>
sys.modules["imageviewer"] = <module whose __path__ is this repo's src/>               # relative imports
importlib.import_module("imageviewer.viewer_api")   # registers routes onto the aiohttp app
```
Routes are then driven over real HTTP with `aiohttp.test_utils.TestServer/TestClient`. Nodes are exercised by calling their `FUNCTION` directly.

**Frontend checks** run the real modules in a page: a small aiohttp server serves `js/` plus stubs for ComfyUI's `scripts/app.js` and `scripts/api.js`, and a test script is injected as `<script type="module">`, writing results to a `window.__*` object that is then read out of the page. Two pitfalls: modules are cached hard (hard-reload, or `fetch(url, {cache: "reload"})` before reloading), and a backgrounded tab throttles timers and stalls `requestAnimationFrame`, which makes anything waiting on a frame appear to hang.

## Architecture

### The panel is one Web Component assembled from mixins

`js/imageViewer.js` defines `<comfyui-image-viewer-panel>` (Shadow DOM, so ComfyUI's CSS cannot reach it), loads `imageViewer.html` / `.css` / the icon JSON by `fetch`, and `Object.assign`s every mixin onto the class prototype. Each `imageViewer_mixin*.js` / feature file is therefore **one flat object of methods sharing one `this`** — there is no inheritance and no module boundary at runtime. Consequences worth knowing before editing:

- a method name collides across mixins silently; the last `Object.assign` wins,
- `this.container` is the `.panel-container` inside the shadow root — reach elements through it (or `this.shadowRoot`), never `document`,
- the panel can be **undocked into another browser window**: use `this._viewerWindow()` and the element's `ownerDocument` rather than the globals, or timers and observers fire in the wrong realm.

Defaults live in **Settings → ComfyUI Image Viewer** (`imageViewer_settings.js`: the table, `pref()`/`setPref()`, `PrefsMixin.applyViewerPref` for a change while the panel is up). A few settings *are* panel state and are written back when the panel changes it (history limit, browser kinds and sequence folding). The pure scene model is told its new-shot and render defaults (`setNewSceneDefaults` / `setRenderDefaults`) rather than importing ComfyUI. The settings are also kept **per OS user**, outside ComfyUI's user directory (`viewer_settings.py`, `~/.comfyui_image_viewer/settings.json` or `IMAGE_VIEWER_SETTINGS`; routes `/imageviewer/settings`): AYON starts ComfyUI with a `--user-directory` inside each project, so ComfyUI's own store is per project. `applyStartupPrefs` loads the file before the panel is built and lays it over ComfyUI's values; every setting's `onChange` writes back. Class names in content rendered into ComfyUI's own DOM (the settings dialog) need a prefix: Tailwind owns names like `fixed`. **Colours** (`imageViewer_theme.js`, `THEME`, `PRESETS`; tests `tests/test_theme.mjs`, `tests/test_theme_browser.py`): the stylesheets (imageViewer.css, Paint's `STYLE` in the editor) keep their colours; each colour writes rules with the SAME selector as the ones it changes (same specificity, later) into one of two `<style data-iv-theme>` appended last to the shadow root - `edit` (the Edit page's own parts, always on) and `chrome` (panels, bars, buttons, Paint, Dependencies; `media` `not all` off a cut's tab only when *Use the colours* is "edit" - the default is "all"; `_themeSync` from `editTlTabShown` / `editTlTabHidden`). `base` is the stylesheet's colour, `def` the default = the Paint preset's (Sebastian 2026-11-10: Paint's look is the new default, presets reach the whole viewer). *Colour preset* (`ImageViewer.Colours.Preset`, `applyPreset` / `writePreset` in the settings) writes a preset's colours into the colour settings; a colour changed by hand sets it to `matchPreset` (a preset or "custom"); neither happens at load (`old` undefined) or during the startup load of the user's file. *Follow ComfyUI* (`COMFY`, "comfy", the preset's default; Sebastian 2026-11-10; `followComfyOnce` in `applyStartupPrefs` moves a kept "paint" - the default before, written by Reset colours - whose colours are Paint's to it ONCE, the hidden `ImageViewer.Colours.FollowSet` saying it is done) is no table: `comfyValues(read, canvas)` maps ComfyUI's palette - CSS variables on the main page's `<html>`, the 1.58 theme tokens (`--background`, `--card`, `--secondary`, `--foreground`, `--border`, `--primary`) before the older comfy_base names (`COMFY_VARS`), LiteGraph's `clear_background_color` for the picture - to every colour; `cssColourReader` resolves var() / color-mix() on a probe and spells them through a 1-pixel canvas; `_themeValues` takes them instead of the settings while following, `_themeWatchComfy` (a MutationObserver on `<html>`'s style / class / data-theme and `<head>`'s children) re-applies on a palette change, and `followComfy` writes them into the colour rows (so a change by hand starts from them and makes the preset Custom; in comfy mode a colour row's change does not repaint). **Popped out**: the styles were copied into the popout's `<head>` at undock, so `_themeHosts` writes the two theme styles there too and `_themeApply` sets the popout body's background (what `:host` is in the page); `_undockInto` calls `_themeApply`. The accent is not a table: `accentRules` scans the shadow root's style sheets for declarations with the stylesheet's orange (`rgb(255, 102, 0)`, as the CSSOM spells it) and writes them again with the accent - so `_themeApply` runs again when Paint brings its own sheet (`imageViewer_paintPanel.js`). A new colour row's selectors must exist in a stylesheet (the node test checks imageViewer.css and the paint editor).

The viewer floats over the canvas (`position: fixed`, appended to `document.body`) or is **docked to the page** as a panel beside it (`imageViewer_mixinPageDock.js`, everything named `pageDock`; not `mixinDock`, which arranges the viewer's inner panels, nor "undock", the popout window). ComfyUI's page is a grid whose outer cells are empty elements (`#comfyui-body-left` / `-right` / `-bottom`); a placeholder of the docked size goes into one, which makes the canvas area yield, and the viewer — never re-parented, that would pause a playing video — is kept exactly over it (`_pageDockSync`, on resize and on its own `style` changing). The cells are page structure, not an API: a missing one means staying floating. Side and size are settings (`Dock.*`).

State that must survive a reload goes through `queuePersistViewerState()` into `localStorage`; a previz scene additionally lives on its node's hidden `scene_data` widget (see below).

### The 3D side

- `imageViewer_scene3d.js` — the scene **data model only**: plain objects, no DOM, no three.js. Items are a flat list with a `parent` id; transforms are `T(position)·T(pivot)·R·S·T(-pivot)·offset`; keyframes are cubic Hermite with per-key easing. Because it is pure data it can be unit-tested under plain `node`.
- `imageViewer_model3d.js` — turns that model into three.js objects and owns the viewport (camera, gizmo, grid, picking, Maya-style navigation, rendering a shot). Each item becomes `root → body → inner(offset) → geometry/children`; the split matters: pivot maths reads *body* space, frozen transforms live on *inner*.
- `imageViewer_mixinPreviz.js` + `previzChannels` / `previzCurves` / `previzRender` / `previzUndo` — the panels and the edits (outliner, channel box, curve editor, render dialog, undo stack).
- three.js is **vendored in `vendor/three/`, deliberately outside `js/`**, so ComfyUI does not serve or import it at startup; it is fetched on demand through `/imageviewer/lib/three/<name>`.
- **Gaussian splats** (.spz, .splat, .ksplat, .sog, and a .ply whose vertices carry `scale_*` + `rot_*` — `isSplatPly`, ComfyUI's own rule) are drawn by Spark (`vendor/three/spark.module.js`, loaded with the first splat) as `SplatMesh` objects in the ordinary scene, turned 180° about X as ComfyUI's viewer turns them. One `SparkRenderer` per view (`_ensureSpark`, remade with the WebGL renderer). A splat has no geometry in three's sense, so a hidden `splatbounds` box beside it is what framing and picking measure. Server side, `model_writer` saves an in-memory `SPLAT` as .ply through core's `SplatToFile3D`, and never converts a splat to a mesh format (`is_splat_file`).

### Server side

- `viewer_api.py` — all `/imageviewer/*` routes, registered at import. Everything taking a path is filtered through `path_access.py`, which confines reads to ComfyUI's input/output/temp plus folders the user allows (`~/.comfyui_image_viewer/roots.txt` — per OS user, NOT in ComfyUI's folder: a launcher's `git stash -u` there swept the old `bepic_viewer_roots.txt` away at every start; that file is still read and adopted — or `IMAGE_VIEWER_ROOTS`). Routes with side effects are POST only. `/imageviewer/roots` (the settings page's folder editor) is the one route that widens that list, so it is fenced by `path_access.may_edit`: same machine (loopback, or the server's own address), ComfyUI's own Origin, JSON POST; `IMAGE_VIEWER_ROOTS_REMOTE_EDIT=1` allows other machines, `IMAGE_VIEWER_ROOTS_LOCKED=1` none; the Host must be this machine's address or name (DNS rebinding). **A route that hands back a file's bytes serves media only** (`path_access.may_serve`: `MEDIA_EXTS`, which includes a glTF's `.bin` / `.mtl`): listing and writing need `is_allowed`, returning content needs `may_serve`. The list never holds a drive root, the home folder or above, a system folder or a hidden one (`too_broad`, enforced when read as well as when edited), and inside an added folder nothing below a dot folder or AppData is allowed. The Comfy registry's reviewer judges exactly this: versions were flagged `arbitrary-file-read`, `path-traversal`, `credential-exfiltration` (read the verdict in `status_reason.message`, `?include_status_reason=true`). **No route may start a process on the host** — the Explorer-opening routes were removed for exactly this reason, and the ComfyUI registry rejected the repo while they existed.
- `usd_io.py` / `abc_io.py` — USD stages and Alembic caches. The viewport speaks glTF only, so both are flattened server-side into a cached GLB "display proxy" and served through the ordinary file route. `abc_io.py` reads the Ogawa container itself (no Alembic bindings exist on PyPI); an Alembic cache is geometry per frame, so its proxy is keyed by `frame`.
- `color_io.py` — the viewer's colour transform: input colourspace → sRGB through OpenColorIO (`$OCIO`, else the built-in config; sRGB and Linear in numpy without it). The target is fixed (the config's sRGB output, the rule `bepic_templates`' colour node starts on); the input is picked in the viewer (`imageViewer_color.js`, the menu in the exposure bar) and travels as `cs=` on `/imageviewer/raw_view`, `/imageviewer/view_file` and `/imageviewer/thumb`. `media_resolve.proxy_for_colorspace` converts and caches one file per source and colourspace (JPEG, or PNG with alpha); without `cs` the older fixed proxy (`proxy_for_display`) still answers. The node therefore hands the viewer the saved EXRs themselves and writes no PNG copies. `buildImgUrl(obj, {noColor: true})` is for anything that is not the picture being looked at. A converted picture takes the **exposure** on the server too (`ev=`, a tenth of a stop per cache entry): input → working linear, multiply, → sRGB. `applyExposure`'s CSS brightness makes up only the stops the element on screen does not already carry (`el._imageViewerEv`, read off the loaded URL in `_setImgSrcCached`), which is all of them for a picture shown as it is and the live preview while a converted frame is on its way (`queueExposureReload`).
- `timeline_io.py` — the cut that lies beside a film, and the **Edit panel** (dock id `editTimeline`, the timeline button in the transport; `imageViewer_editTimeline.js`). A cut is an OpenTimelineIO file; one lies beside a film of the same name (`cut.mp4` / `cut.otio`; agentY's edit stage writes one, and so can Resolve or Premiere), one is started in the panel (New, or the first clips added). **Every open cut has a tab of its own** (key `edit:…`, no media frames, kept by the stale-tab sweep) **and plays there before anything is rendered** - see *Playing a cut* below. On a film with a cut beside it the timeline button lights up and opens that cut's tab; it is not opened by itself. The panel shows the cut of the tab that is up (`_editTlTab`; the others wait in `_editTlCuts`, all of them in localStorage `imageviewer.viewer.edits`, each with how it is looked at - zoom, track heights, solo - as `view`). **The Edit panels - Edit, Inspector, Effects, Mixer, Source (`EDIT_PANELS`) - are up only while a cut's tab is**: `switchTab` hides them for any other tab (`editTlTabHidden`) and brings back the ones that were open (`_editTlWanted`, localStorage `imageviewer.viewer.editPanels`) with the next cut. The Edit panel is a column of track headers that stays and, beside it, a strip as wide as the zoom makes it (`view.zoom`, Ctrl+wheel about the pointer, the wheel or the middle button to pan): a ruler (drag to scrub) that stays on top, then two sections that scroll up and down on their own - the video tracks (texts, the higher video tracks, V1) above a splitter, the sound (A1, the sound tracks) below it; see *The timeline's ruler, readout, sections and heights* below. A header carries the track's switch (off: saved, not rendered), its solo (`view.solo`, a way of looking: played, neither saved nor rendered - `liveTracks`) and, on its lower edge, its height. A clip is coloured by right-click or in the Inspector (`metadata.imageviewer.color` in the file). A dissolve is a bar over its join (`.edit-mix`, selection kind `mix`): its edges resize it, the Inspector has its length. A clip's body is dragged along its track or onto another one (`_editTlTrackUnder`, `transferClip`; a ghost shows where it would land): onto V1 it lies over what is there (an overwrite, `overwriteV1`; Ctrl+Shift: between the shots, an insert), onto any other track it is placed; off V1 it leaves a gap (`liftV1`). It is an editor: drag a shot's edge to trim, a shot to move, a text to move; drop rows of the file browser / history thumbs (the `application/x-imageviewer-history` payload) or a node dragged off the canvas (the page is watched for the release - LiteGraph keeps the pointer - and the node is put back) to add clips. **Tracks** (`cut.tracks`, `timeline_io.extra_tracks`): V1 is the cut itself - one shot after the other, dissolves, and GAPS (see *Modes, gaps, linked sound, snapping* below) - and A1 the bed under the whole film; every further track holds clips that are PLACED (`at`), and nothing moves when one does. A clip on a higher video track covers what is under it, **picture and sound** (the player has one element sounding at a time, and `timeline_render.covered` / `film_sound` follow the same rule so that the film is what was played); sound-track clips lie under everything. In the file they are OTIO tracks with gaps, the first audio track always being A1 (an empty one is written when a cut has sound tracks but no bed, or the first of them would be read back as the bed). Two clips of one track that share a moment: the later one is on top in the page, and on save the earlier ends where the later begins. An edit without a `tracks` / `off` key (an older page) leaves what the file holds of them alone. The numbers of the selection are in the **Inspector** and transitions, texts and plain colours in **Effects** (`imageViewer_editPanels.js`): the Inspector is in the viewer's own look (the panels' ground, the Parameters header, the Edit panel's buttons, cyan numbers - on purpose not any other program's; it was restyled once for looking like one) and holds the clip's name, tabs (Video / Audio / Timing / File; Title for a text, Transition for a dissolve), sections with a switch and a reset, a reset per row - and every row is something the preview plays and the render writes, no control that only looks like one. **A clip's transform, cropping and opacity** (`clip.fx`, `metadata.imageviewer.fx`; the table `FX` is in `timeline_io.py` and in the data module, and the two must agree): zoom, position and anchor point as fractions of the frame (y UP), rotation in degrees clockwise, a crop per side, opacity; `toff` / `coff` / `ooff` switch a section off and keep its numbers (`clipFx` is the effect as DRAWN, `rawFx` as its numbers stand). One arithmetic, twice: `fxPlace` gives the layer its CSS transform (put after the viewer's own) and a clip-path that is the frame taken back through that transform and cut to the crop; `timeline_render.lay` does the same with an affine transform and an alpha that is the picture's box less its crop - a change to one is a change to the other, and `fx_check`-style pixel tests of the render are cheap to rebuild. A clip on a higher track that no longer covers the frame has what is beneath it as `under` with `over: true` (`pictureAt`) and the player draws that ONE picture beneath, as it does for a dissolve; the render draws them all. A slider is live while dragged (`editPlayFxLive`, which changes no cut - a redraw would take the slider from under the pointer) and commits when let go. Not there, rather than there and dead: pitch and yaw, crop softness, dynamic zoom, speed, keyframes. An Effects item is dragged onto the timeline (`application/x-imageviewer-effect`) or double-clicked; a plain colour is a PNG the server makes (POST `/imageviewer/timeline_solid`, one file per colour and size), because a clip is a piece of a file; a text made here is a marker with no `ref`, drawn at once. Save (POST `/imageviewer/timeline`) writes the cut into the `.otio` and stamps it (`metadata.imageviewer.edited`); the film it lies beside is not touched. A tab closed with unsaved changes says so once and stays. **Render** (POST `/imageviewer/timeline_render`, `timeline_render.py`) makes the film of the saved cut in this process through PyAV - a ComfyUI dependency, so no program is started and the no-process rule holds: shots scaled to fit and padded, a dissolve blended frame by frame, the shots' own sound and the bed mixed in memory (hence `MAX_SECONDS`). It never writes over the film a cut lies beside (that may be somebody's render): the result lands by the export rule as the next version, with its own `.otio` marked `rendered`. **Titles** are clips (see *Titles* below); the render draws them (`timeline_render.title_frames`, through `title_render`), the Edit tab draws them while it plays, the same way. `texts_left_out` stays in the answer, at 0; `notes` says when a title's font was not on the machine. With no film, dropped clips start a new cut, saved by the export rule (kind `edit`). Rules worth knowing: the panel works on clips at FULL length with the dissolve leading into each (`timeline_io.editable`), OTIO lets clips meet mid-dissolve (`rebuild`) - a dissolve is split into whole frames that add up, or the film comes back a frame short; an existing clip is saved by `ref` (its place in the file) so everything another program wrote into it survives, a new one by `file`, which must pass `path_access.is_allowed`; a clip's length comes from POST `/imageviewer/timeline_probe` (PyAV reads the container header in this process - the server may not start a process to ask), and only where that fails from the browser (`<video>` metadata). `imageViewer_editTimelineData.js` is the arithmetic (pure, every edit returns a new cut; run it under node after a change).
- **Cutting like an editor** (`imageViewer_editKeys.js`, `imageViewer_editMedia.js`, `imageViewer_editAuto.js`, all mixins onto the panel; their arithmetic in `imageViewer_editTimelineData.js`, tested in `tests/test_edit_timeline_data.mjs`, the panel in `tests/test_edit_timeline_browser.py` against `tests/harness/edit.html`). **Undo**: every change of the cut goes through `_editTlApply`, which pushes the cut it replaces onto a stack per cut's tab (`_editTlHistories`, `historyPush` / `historyUndo` / `historyRedo`; not kept across a reload); a drag is one step - `_editTlDrag` records the cut of the press when it is let go, and `_editTlApply` stands down while `_editTlDragging`. A save renumbers the file's items, so the stacks are `detach`ed then (their clips held by `file`, not `ref`). **The blade** (`_editTlBlade`, toolbar ✂ or B) cuts the clip clicked (`splitClip`; both halves keep the clip's `ref` - `rebuild` deep-copies the item it names, so another program's metadata survives in both; no dissolve is made; refused in a dissolve or a frame from an end); Ctrl+B / S cut at the playhead (`splitAt`: the selected clip, else every clip there); Del `liftClip` (a gap stays - on V1 too, `liftV1`; a selected gap is closed), Shift+Del `rippleDelete`; a clip linked to its sound / picture takes it along (`deleteWithLink`); the blade cuts a linked pair together (`splitWithLink`). **Keys** (`editTlKeyDown`, asked first by `handleKeyDown`, which runs on the viewer's window, popped out or not): they act only while the composed path holds the panel's body - it takes the focus on a press (`tabIndex`, a capture `pointerdown`) - and never in a field (`handleKeyDown`'s `isTyping`, which now counts a SELECT); a key it takes is `stopImmediatePropagation`ed, so ComfyUI's own Ctrl+Z never sees it. J runs backwards on a timer, I / O set the transport's own `playbackRange` (see *In and out* below), Up / Down go to `editPoints`. **Drops** (`_editTlAdd`): the history payload, desktop files (`Files`; copied by POST `/imageviewer/timeline_upload` into `<input>/edits` - media only, base name made safe, same name and size used again, never written over; a viewport drop on an Edit tab does the same), ComfyUI queue / assets pictures (`text/uri-list` of its `/view`, found by POST `/imageviewer/timeline_locate`, as are history items that only have `filename`), canvas nodes (the track under the release is used too). Films and pictures go on V1 between the shots or placed on a video track; sound always to a sound track (the one dropped on, the first, or a new one). A drop snaps (`_editTlSnap`, through the one snapping - `_editTlSnapAt`) and the target row is lit (`.landing`); a drop inside a V1 gap is placed at that moment (`insertAt`), elsewhere on V1 it is an insert. ## Import and export: one vocabulary, one set of rules

The viewer's ways in and out grew one feature at a time and were then brought under one rule. New work follows it.

**Four words, and they do not overlap.** *Open* shows a file in the viewer. *Add* brings a file into what is being worked on (a scene, a cut). *Save* keeps the working document (a scene, a cut) where it already lives. *Export* writes a deliverable (a film, frames, a USD stage, a PNG). "Render" is the button inside an export dialog, not a fifth idea. No "Import", "Load" or "Download" in new UI.

**`export_rules.py` decides, for every export:**
- *what a format is* (`VIDEO`, `video_settings`): a container means the same codec wherever it is offered. MOV is ProRes 422 unless H.264 is asked for; MP4 is H.264; WebM is VP9. Quality is `high` / `medium` / `low`, and each encoder's number for those is there and nowhere else. `/imageviewer/export_options` serves the table to the page.
- *where a file goes and what it is called* (`target`): with a sequence and shot (a context node on the canvas, sent by the page as `context`) the bEpic layout, `<Seq>/<Shot>/<kind>/v###/<shot>_v###_<name>.<ext>`; without, `imageviewer/<kind>/<name>_v###.<ext>`. Under ComfyUI's output folder, always the next version - an export never writes over an earlier one. `/imageviewer/export_target` previews it without creating anything.

**The shared pieces** (`imageViewer_exportUI.js`, plain functions): `openExportDialog` (name, format, codec, quality, the feature's own rows, and "Goes to" - the path asked from the server before anything is written), `openFilePicker` (the file browser's listing as a question: `/imageviewer/browse` again, so the same folders and refusals; it opens where the kind is kept, `/imageviewer/export_places`, and remembers the folder per `id`), `notice` (a toast; there is no `alert()` and no `prompt()` for a path anywhere), `canvasContext` (the sequence and shot the graph names). `sequence_target` / `sequence_frame` are the rule for numbered frames: in a shot they lie in the version's folder, without one in a folder of their own name.

**Where each feature stands** - all of them follow the rule:
- *Edit panel*: Export… renders by the rule; a new cut is saved by it. Export to Resolve… lands beside the cut, as a folder, and takes the next version too.
- *Annotations*: versioned, in the shot's folder when there is one.
- *Previz*: Save scene, Export USD (dialog, versioned), Open scene, Open USD / Alembic (picker). The render lands by the rule too: frames are uploaded into `output/previz/<name>/` (the take's working folder), then encoded to the next version, or - kept as stills - moved (`/imageviewer/previz_publish`). `output/previz/<name>.latest.json` (`previz.note_render` / `latest_render`) says where the take went, which is how the scene node still finds it by `render_name`; a new take removes the note, never the earlier version. Takes and scenes from before the rule (`output/previz/<name>.mp4`, `output/3d_scenes`) are still read, and the picker offers the old folder.
- *What is on screen* (`imageViewer_exportView.js`, `export_view.py`, POST `/imageviewer/export_view`; the Export Frame or Clip command - it has a hotkey and no button): the current frame as a PNG, or the whole clip / sequence as a film - those two and no more. A picture is exported as shown (through the colourspace picked, without exposure); a video is a one-clip cut through `timeline_render`, so it keeps its sound. On a 3D scene it opens the previz render dialog, on an Edit tab the cut's export.
- *A frame dragged off the timeline* goes to `<kind folder>/frames/`, named after its clip and frame and so not versioned: the same frame twice is the same file.
- *Send to Viewer*: a `codec` widget, **last** among its inputs (saved workflows hold widget values by position - anything new goes after it), shown for `mov`; `auto` is the rule's default, so a MOV from the node is ProRes now unless H.264 is picked.

**A film a `<video>` cannot play** (ProRes; 10-bit or 4:2:2 H.264) is shown through an H.264 copy made on first request and cached in temp (`media_resolve.video_proxy`, called from `_file_response`; a key frame a second). Both copies clear each decoded frame's picture type before encoding (`_no_picture_type`): libx264 takes an I as an order, so a ProRes film (every frame an I) came out all key frames and stuttered when played. Only what is looked at goes through it: exports, cuts and extracted frames read the film itself.

**In and out of a panel are buttons at the top left of its body**, at the Outliner's size (`.previz-btn.previz-icon`), in one order: New, Add (Lucide's circle-plus, `icon-circle-plus`), then what the panel has of its own, then Save / Export (`icon-save`, a menu). Outliner: New · Add · Edit · Save/Export/Render. Edit panel: New · Add (files, canvas nodes, a new track) · Save/Export, and no second Save at the right. They were once two small glyphs in the title bar and were overlooked there; a title bar holds a name and a close button, nothing else. A panel that takes files takes the same drop - the `application/x-imageviewer-history` payload - as the Edit panel and the viewport (`previzAddDropped` for the Outliner; on an Edit tab the viewport adds clips).

**Folding and maximising a panel** (`imageViewer_mixinDock.js`; Sebastian 2026-11-10, Houdini's maximise asked for, its split tree left for later): two `.pt-btn`s left of the close in every title bar (`#<id>-fold-btn`, `#<id>-max-btn`, Lucide chevrons / maximize-2 - minimize-2, `_dockBarIcons`), a double-click on the title folds too. `collapsed: true` on the layout entry (kept by `applyDockData`; a tab group folds as one; `dockToggleCollapsed`, `isPanelCollapsed`): `.dock-collapsed` shows the title bar only, flex `0 0 auto`, no splitter beside it, the bottom rail `auto` high when all its panels are folded. `_dockMaxId` (not saved; `dockToggleMaximized`, `isPanelMaximized`): `_dockMaxSync` from `applyDockLayout` makes that panel `position: fixed` over the container from `.main-area`'s top to `.controls`' top (fixed, because `.main-area` clips), re-placed every animation frame of its own window while up, so moving or resizing the viewer or popping it out keeps it in place. Test `test_a_panel_folds_…` in `tests/test_viewer_tabs_browser.py`. (`_dockEntry` is the older `{side, entry}` finder; `_dockEntryOf` returns the entry.)

**Dock panels as tabs** (`imageViewer_mixinDock.js`): a panel dropped onto the MIDDLE of another (the outer thirds still mean before / after) shares its place - two more fields on a layout entry, `tab` (the group's name) and `behind` (every member but the one in front). A panel that is behind is open (`isPanelDocked`) but not drawn (`isPanelFront`); the front panel's title bar names them all, and a press on a name brings that one up (`dockTabFront`, which also fires `_onPanelShown`). Anything that toggles a panel should bring a behind one to the front rather than close it (the bar's groups do). `dockPanelTo` takes a panel out of its group; members stay next to each other in the rail's list (`_dockRegroup`).

**The lower bar** (`imageViewer_barGroups.js`): playback at the left; then the panels in three groups, each one button that opens a short menu upwards - ComfyUI (its own logo, from the frontend's `/assets/images/`): History, Parameters · 3D (Lucide `box`): Outliner, Channel Box, Curve Editor (the panel once called Animation Curves; its home is the bottom rail), on a 3D tab · Timeline: Edit, Effects, Inspector; everything else (layout, shape overlay, page dock, files, run, clear) at the right end. It is done with CSS `order` and a spacer: no button is re-parented, the old History / Parameters buttons stay in the DOM hidden and still carry the handlers and the lit state. A new panel goes into a group, not onto the bar.

**Where an export ends up on screen**: `exportLanded(paths)` puts it in the History (made in the one Viewer tab, `showInViewerTab(.., {show: false})`), without switching to it. The Edit panel's film still opens in a tab of its own, beside the cut's, and an annotation joins the History, made in the tab it was drawn on.

**Kept on purpose:** the old routes' behaviour without `rule: true` (an older cached page, agentY) - new behaviour is asked for by that flag or a new route, never by changing what an existing request does.

### Paint (a picture in layers)

A small picture editor for the user and the agent: layers, a brush, selections, masks, adjustment layers, text, crop / resize, and Generate (heal, extend, upscale, and AI fills through agentY). Props, Tool, Effects and Generate ship as tabs of one place (`tab: "paint"`); a layout saved before a panel existed gets it as a tab behind its `DOCK_PANELS[id].tabWith` (`_normaliseDockLayout`). `paintTabLeave` keeps which were in front (`st.front`) and `paintTabEnter` puts them back; `host.showPanel(part)` / `paintShowPanel` take a part or an id. No time: the bar counts no frames there (`getImgCount` 0, `setFrame` a no-op). Opened from the bar's Paint group, a history item's "Edit in Paint", the file browser (kind `paint` = .ora / .psd, or a picture's menu), or `imageviewer.paint.open` (POST `/imageviewer/push` with `panel: "paint"`, or an .ora / .psd pushed). - **One arithmetic, twice**: `paintData.js` and `paint_math.py` composite, blend (W3C separable formulas; "add" is Linear Dodge), adjust and filter in the same order with the same rounding (`floor(x * 255 + 0.5)` after every layer), so an export, the .ora's merged image and the agent's result are the picture the user saw. - **Sessions and raw pixels**: the server holds each open document as a session (`_Book`, at most 6, random 32-hex token). The .ora is OpenRaster (Krita, GIMP) plus our `imageviewer.json` (adjustment layers, masks, text, the selection). The .psd is 8-bit RGB with pixel layers, masks, blend modes and the merged image; adjustment layers are BAKED on export (the answer says so); reading a .psd takes its pixel layers and names what it left out.
- **The agent** (agentY-core's `edit_image`): POST `/imageviewer/paint/doc` with `doc` (a path or token) and `ops` (`paint_ops.OPS`, all or none, layers named from 1 at the TOP, by name or "active"); without ops it answers the outline. ### Comp (a node graph of pixel operations)

A space of its own beside Motion (Sebastian 2026-11-10: two spaces that share dialogues; Comp opens on the node editor; NO ComfyUI node - a render goes to the History and onto the canvas). Files: `js/imageViewer_compModel.js` (the document and the pixels, pure), `imageViewer_compEditor.js` (graph, Properties, Layers and the picture; knows nothing of the viewer), `imageViewer_compPanel.js` (`CompPanelMixin`, the glue), `imageViewer_compComfyTab.js` (the graph in ComfyUI's bottom panel); server side `comp_model.py` (the numpy twin), `comp_io.py` (files, footage, writers), `comp_routes.py` (the routes).

- **The document** `*.comp.json` = `{comp: 1, format: {width, height, fps, frames}, nodes: [{id, type, name?, x, y, disable?, inputs: [ids], <params>, tracks?}], output}`. The GRAPH is what is stored; Layers is `layerStack(comp)`, a reading of it (the B pipe's Merges are layers, a Merge's A branch its picture, a Merge inside an A branch a group), and every Layers edit is a graph edit (`addLayer`, `moveLayer`, `removeLayer`). Node types `NODE_TYPES` (read, constant, roto, merge - Nuke's operations -, copy, transform, crop, grade, colorcorrect, lumakeyer, chromakeyer, erode, laplacian, channelmerge, channelmath, ocio_colorspace, ocio_display, keyer, blur, motionblur, depthblur, defocus, shuffle, premult, unpremult, retime, vectors, output) are in both languages and the parity test compares the tables. Keys are Motion's (`tracks: {param: [{f, v, ease, ti?, to?}]}`, `valueAt` from `imageViewer_mgScene.js`, ported to Python), so Properties uses Motion's rows, stopwatch and diamond (`MG_CSS`, exported from `imageViewer_mgEditor.js`) and Motion's `History` for undo.
- **The heavier nodes** (`imageViewer_compOps.js`, imports nothing - compModel imports it and re-exports `blank` / `blurImage`; the numpy twins are in `comp_model.py` itself, which must stay loadable on its own): Crop (pixel area, or a ramp of `softness` at the centres), Shuffle / Copy (the numbers as they stand, premultiplied), Keyer (chroma: chromaticity c / (r+g+b) against the screen's, as a share of the screen's distance from grey; despill pulls the screen's strongest channel to the larger of the other two), Roto (the viewer's roto data in `roto` - see the Roto bullet below -, `roto_matte` = `roto_raster.rasterize(.., frames=[f])` on the server, the page's `ctx.matte` in renderNode), Vectors (Horn-Schunck on a pyramid, 2 warps a level, Jacobi; `detail` half / quarter skips the finest levels and brings the field up bilinear; out rg = forward, ba = backward, in COMP pixels), MotionBlur (a gather along the vectors, edge repeated), DepthBlur (`layers` blur sizes, each pixel's circle of confusion shared between the two nearest, numerator and weight blurred alike; `filter` lens blurs each through Defocus's disc), Defocus (`apertureRows` / `aperture_rows`: the aperture's span per row - a disc, or a polygon of `blades` with `rotation` and `aspect` -, each pixel the mean over it from running sums along the rows, a row's end pixels weighted by their cover; `bloom` multiplies rgb by 1 + bloom x (L - threshold) above the threshold first; the edge repeated). **Time**: `renderNode` memoises by node AND frame; Retime, Vectors and MotionBlur without vectors render their input at other frames, and `sourceNeeds(comp, id, frame)` lists every `{node, frame}` a picture reads (the editor loads them all first, keyed `id@frame`). `HEAVY` nodes' results are kept between renders in `ctx.cache` keyed by frame, scale and `upstreamKey` (their own and every upstream node's settings). Everything is float64 between steps and stored float32 where the other twin stores it: keep the operation order identical (no `**`, explicit products). - **ColorCorrect** (`imageViewer_compColor.js`, imports nothing; twin `color_correct_image` in comp_model.py; Sebastian 2026-11-10: "more like Color Finesse than Nuke's ColorCorrect"): params `<range>_<name>` for master / shadows / midtones / highlights (hue, saturation %, brightness, contrast %, gain / gamma / pedestal and their `_r` `_g` `_b`, `tint_hue` / `tint` = the hue offset wheel), `contrast_centre`, `shadow_end` / `highlight_start` (`rangeWeights` on luma^(1/2.2), smoothsteps, normalised), `secA_*` / `secB_*` (an HSV hue / saturation / luma qualifier, then hue / saturation / brightness), `mix`, `view` (a range's or a secondary's matte). - **Reformat** (`reformatLayout` / `reformat_layout`): the comp has ONE size, so a Reformat lays its input into a box INSIDE the frame (width x height or the comp x scale; resize none / fit / fill / width / height / distort on the input as turned; flip / flop; centred or at the bottom left; `black_outside` crops to the box). A different output resolution is the comp's format.
- **Light** (`imageViewer_compLight.js`, imports only compOps; twins `glow_image`, `flare_image`, `flare_ghosts`, `dirt_spots`, `mulberry32` in comp_model.py): Glow (threshold / softness on luminance or max, tinted, `steps` blurs halving from `size`, averaged x intensity, added or `effect_only`); LensFlare (inputs src, dirt; `position` in comp px, null = the middle; sizes are shares of the diagonal x `size`; glow (Rg²/(Rg²+r²))², rays exp(-perp²)(1-along/L)², a halo per channel at radius x (1 + (k-1) 0.03), ghosts at light + t x 2 (centre - light) from `mulberry32(seed x 7919 + 17)`, disc or polygon (`polyEdge`), dirt = the dirt input's luminance or spots from `mulberry32(seed x 104729 + 3)`, lit by Rd²/(Rd²+r²)). The JS loops per pixel, numpy per ghost / spot in its box: the order of the sums is the same.
- **Clean room** (Sebastian 2026-11-10, as for Paint): every Comp node is written from published maths and observed behaviour; no code, shaders or assets from Nuke, After Effects, Color Finesse, Keylight or GPL sources. docs/comp.md says so.
- **One arithmetic, twice**: linear, premultiplied RGBA float, bilinear at pixel centres with transparent outside, Paint's three box blurs for a Gaussian, Nuke's Merge and Grade formulas. `renderNode(comp, id, frame, {scale, source})` in JS at a proxy scale, `render_node` in numpy at full size; `tests/test_comp_parity.py` (through `tests/comp_parity.mjs`) compares them float for float. Change one, change the other. A source may come SHRUNK (`ow` / `oh` = the file's size): `fitMatrix(.., k)` with k = scale x ow / w, which is what "none" needs.

### Worlds (branch `worlds`)

Walkable worlds built from reference images. The viewer only *shows* them; they are *made* by a separate repo,
`ComfyUI-bEpicWorlds` (sibling folder in custom_nodes; library, nodes, `/bepic_worlds/*` routes, MCP server, CLI).
The contract is the scene schema — `SCHEMA.md` there, `imageViewer_worldData.js` here.

- `imageViewer_worldData.js` — the world item kinds (environment, terrain, scatter, depthmesh), camera `reference`,
  scene `walk` / `world`, as pure data; `parseScene` reads them through it.
- `imageViewer_world3d.js` — a mixin on Model3DView (installed with `defineProperties`: it has a getter): sky/sun/fog
  replacing the studio rig, terrain, instanced scatter with wind, depth mesh, walking, reference overlay, feedback pins.
  World items rebuild when `_worldKey` (their settings as JSON) changes.
- `imageViewer_previzWorld.js` — the panel side: Add → World, channel-box rows from `WORLD_FIELDS`, Walk/Note buttons,
  notes POSTed to `/bepic_worlds/feedback` (kept in the scene only when that route is missing).
- A world arrives as a normal `imageviewer.viewer.update` with `scene_replace` (replace the tab's scene), `tab_label` and
  `focus_tab`; tab keys start `world:` and survive the stale-tab sweep.
- A world built around a whole-picture model has it as an ordinary `model` item with id `scene` (placed by the pack's
  `set_scene_model`), so the World tab is the only 3D view. An HDR sky (`sky.hdr`, `.hdr`/`.exr`) is read by the
  vendored `HDRLoader` / `EXRLoader` from `/imageviewer/view_file?…&raw=1` (`raw` skips the PNG display proxy, which would
  clip it); with `sky.lighting` it is also the world's PMREM environment, and `render.reflections: "sky"` keeps the
  cube capture from replacing it (`_worldSkyLight` / `_worldDropSkyLight`).

### Keys and curves (previz and roto)

- One key bar in the transport (Set Key, Delete Key, Autokey, ease menu), built in `previzEnsureKeyBar`; `_keyBarContext()` decides whether a press keys the previz scene or the roto tool's shapes, and `keyBarSync()` shows it for whichever is up.
- The drawing tools' options (Roto, SAM3 points/boxes, Annotate) live in the **Parameters** panel: while a tool is on, `_toolShowDock` puts it in `tool-mode` (header names the tool, lock hidden, node widgets hidden, the selection monitor paused via `_paramsToolMode`) and each tool fills `this._toolPanel`, a sibling of `#params-content`. The panel opens with the tool, closes after it only if it was closed before, and goes back to the node on 3D tabs. Nothing floats over the picture but the toolbar.
- Roto and SAM3 follow the canvas selection: selecting a Roto / SAM3 Collector node brings its tool up, selecting anything else puts a tool brought up that way away again (`_toolFollowSelection`, called from the params monitor's tick; the params lock holds it). Their toolbar buttons only create a node (`createToolNode`, left selected) — the selection does the rest. Annotate has no node and still toggles.
- Two dock panels, one look: previz's **Animation Curves** (`imageViewer_previzCurves.js`, value graphs) and **Roto Curves** (`imageViewer_rotoCurves.js`, a shape's timing between keys). Both are built from `imageViewer_curveUI.js` (panel skeleton, list/graph splitter, tangent arms), which stays plain functions so the two mixins can't collide.
- **Node parameters** can be keyed too, on nodes that declare an optional `animation` STRING input whose spec lists `bepic_animatable` names (the bEpic image nodes in `bepic_templates`: Transform, Grade, ColorCorrect, Blur, Merge, Constant, Crop, Retime). The keys are JSON in that hidden widget — a real input, so a changed curve re-runs the node. `imageViewer_paramAnimData.js` is the format and the maths (pure); `bepic_templates/bepic_anim.py` renders it and **must interpolate identically** (compare the two on random tracks after any change). `imageViewer_paramAnim.js` puts key toggles on the Parameters rows (Nuke rules: an animated value keys itself when edited; Alt-click drops a track, leaving the widget at the frame's value), and makes the key bar's third context, `params`; `imageViewer_paramCurves.js` is the **Parameter Curves** panel (dock id `paramCurves`, opened by ∿ in the Parameters header).
- A roto key's `tangents[frame]` carries `{ox, oy, ix, iy, hold}`; `roto_raster.py` must interpolate exactly as `_rotoSegEase` does, or the mask a node renders won't match the viewer.
- Each roto shape has a `mode` (union, plus, minus, intersection, xor — the bEpic Nuke ChannelMerge operations, shape = A, the shapes before it in the list = B, clamped after each). `roto_raster.MODES` / `_merge` and the viewer's `ROTO_MODES` / `rotoMerge` must stay identical. Intersection is the one mode that changes pixels outside a shape's region (to 0), so the renderer handles it on the whole frame. The viewer's mask preview composites the same way on a canvas (`_rotoRenderComposite`), sized to the viewport — not to `#imageviewer-tool-draw`, which keeps its default 300x150 box and draws the rest as overflow.
- The Roto toolbar button binds to a selected Roto node instead of creating one (`selectedToolNode`); the Roto Curves panel opens only from its button.
- `roto_raster.rasterize` stays fast by working each layer only inside the box its outline + feather/dilate/blur can reach, reusing the mask of any frame whose outlines equal an earlier one's, and rendering the rest on a thread pool (`IMAGE_VIEWER_ROTO_THREADS` caps it). A change to the matte maths must keep the box margin wide enough (3σ per blur, the dilate radius) or it clips; compare its output against the old renderer's pixel for pixel.
- Anything that moves the frame must call `_toolsFrameChanged()` (image sequences in `setFrame`, videos in its video branch and `_videoOnTimeUpdate`), or the roto overlay lags until the next unrelated redraw.

### Hotkeys

`imageViewer_keymap.js` is the single table feeding three consumers: ComfyUI's command list (so every action is rebindable in Settings → Keybinding), the panel's own key handler (which answers while the viewer is hovered), and the in-viewer help overlay. Add actions there, not ad-hoc listeners. A combo ComfyUI already owns ships unregistered and still works while hovered.

## Publishing

`.github/workflows/publish.yml` publishes to the Comfy registry **on any push to `master` that touches `pyproject.toml`**, and only from `szprivate/ComfyUI-ImageViewer`. So: bumping `version` in `pyproject.toml` *is* publishing. Push other changes freely; touch that file only when a release is intended.

Remotes: `origin` = szprivate (dev, and the one that publishes). There used to be a second remote for bEpic-studio (the org); check `git remote -v` before pushing.
