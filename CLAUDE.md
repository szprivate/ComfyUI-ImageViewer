## What this is

A ComfyUI custom node pack whose real product is a **frontend viewer panel**: a floating, dockable image/video/3D viewer with tabs, history, comparison, playback, a file browser, drawing tools and a 3D previz tool. Python here is the thin half — four nodes and a set of `/bepic/*` HTTP routes; the JavaScript in `js/` is the thick half.

`__init__.py` exports the nodes, imports `viewer_api` (which registers the routes as a side effect of import), and sets `WEB_DIRECTORY = "js"`, which is how ComfyUI serves the frontend from `/extensions/ComfyUI-ImageViewer/`.

## Running and testing

Nothing to build: the JS is plain ES modules served as-is, and Python needs no compilation step. There is a test suite in `tests/` (`D:/AI/agentY/.venv/Scripts/python.exe -m unittest discover -s tests` and `node --test tests/*.mjs` - node's own discovery finds nothing, the files are named `test_*.mjs`); the tests that need PyAV (`test_timeline_media_routes.py`) are skipped there and run with ComfyUI's interpreter, `D:/ai/comfyui/.venv/Scripts/python.exe -m unittest discover -s tests -p "test_timeline_media_routes.py"`. Browser tests serve `tests/harness/*.html` (the real viewer js, ComfyUI stubbed) through `tests/harness/server.mjs` with Playwright. Beyond those, two things stand in for a test runner, and both are worth rebuilding when you change anything non-trivial.

Use ComfyUI's own interpreter, never a bare `python`:

```bash
D:/ai/comfyui/.venv/Scripts/python.exe -s <script>      # -s: ignore user site-packages
node --check js/bEpicViewer_model3d.js                  # the only "lint" the JS has
D:/ai/comfyui/.venv/Scripts/python.exe -m py_compile viewer_api.py
```

**Python-side checks** run the real modules with ComfyUI stubbed, in a scratch directory (not in the repo). The pattern each such script follows:

```python
sys.path.insert(0, r"D:\ai\comfyui")          # for folder_paths and comfy_extras
import folder_paths
folder_paths.set_output_directory(tmp); folder_paths.set_input_directory(...)   # scratch dirs
sys.modules["server"] = <module exposing PromptServer.instance.app + send_sync>
sys.modules["bepic"] = <module whose __path__ is this repo>                     # relative imports
importlib.import_module("bepic.viewer_api")   # registers routes onto the aiohttp app
```
Routes are then driven over real HTTP with `aiohttp.test_utils.TestServer/TestClient`. Nodes are exercised by calling their `FUNCTION` directly.

**Frontend checks** run the real modules in a page: a small aiohttp server serves `js/` plus stubs for ComfyUI's `scripts/app.js` and `scripts/api.js`, and a test script is injected as `<script type="module">`, writing results to a `window.__*` object that is then read out of the page. Two pitfalls: modules are cached hard (hard-reload, or `fetch(url, {cache: "reload"})` before reloading), and a backgrounded tab throttles timers and stalls `requestAnimationFrame`, which makes anything waiting on a frame appear to hang.

## Architecture

### The panel is one Web Component assembled from mixins

`js/bEpicViewer.js` defines `<bepic-viewer-panel>` (Shadow DOM, so ComfyUI's CSS cannot reach it), loads `bEpicViewer.html` / `.css` / the icon JSON by `fetch`, and `Object.assign`s every mixin onto the class prototype. Each `bEpicViewer_mixin*.js` / feature file is therefore **one flat object of methods sharing one `this`** — there is no inheritance and no module boundary at runtime. Consequences worth knowing before editing:

- a method name collides across mixins silently; the last `Object.assign` wins,
- `this.container` is the `.panel-container` inside the shadow root — reach elements through it (or `this.shadowRoot`), never `document`,
- the panel can be **undocked into another browser window**: use `this._viewerWindow()` and the element's `ownerDocument` rather than the globals, or timers and observers fire in the wrong realm.

Defaults live in **Settings → bEpic Viewer** (`bEpicViewer_settings.js`: the table, `pref()`/`setPref()`, `PrefsMixin.applyViewerPref` for a change while the panel is up). A few settings *are* panel state and are written back when the panel changes it (history limit, browser kinds and sequence folding). The pure scene model is told its new-shot and render defaults (`setNewSceneDefaults` / `setRenderDefaults`) rather than importing ComfyUI. The settings are also kept **per OS user**, outside ComfyUI's user directory (`viewer_settings.py`, `~/.bepic_viewer/settings.json` or `BEPIC_VIEWER_SETTINGS`; routes `/bepic/settings`): AYON starts ComfyUI with a `--user-directory` inside each project, so ComfyUI's own store is per project. `applyStartupPrefs` loads the file before the panel is built and lays it over ComfyUI's values; every setting's `onChange` writes back. Class names in content rendered into ComfyUI's own DOM (the settings dialog) need a prefix: Tailwind owns names like `fixed`.

The viewer floats over the canvas (`position: fixed`, appended to `document.body`) or is **docked to the page** as a panel beside it (`bEpicViewer_mixinPageDock.js`, everything named `pageDock`; not `mixinDock`, which arranges the viewer's inner panels, nor "undock", the popout window). ComfyUI's page is a grid whose outer cells are empty elements (`#comfyui-body-left` / `-right` / `-bottom`); a placeholder of the docked size goes into one, which makes the canvas area yield, and the viewer — never re-parented, that would pause a playing video — is kept exactly over it (`_pageDockSync`, on resize and on its own `style` changing). The cells are page structure, not an API: a missing one means staying floating. Side and size are settings (`Dock.*`).

State that must survive a reload goes through `queuePersistViewerState()` into `localStorage`; a previz scene additionally lives on its node's hidden `scene_data` widget (see below).

### The 3D side

- `bEpicViewer_scene3d.js` — the scene **data model only**: plain objects, no DOM, no three.js. Items are a flat list with a `parent` id; transforms are `T(position)·T(pivot)·R·S·T(-pivot)·offset`; keyframes are cubic Hermite with per-key easing. Because it is pure data it can be unit-tested under plain `node`.
- `bEpicViewer_model3d.js` — turns that model into three.js objects and owns the viewport (camera, gizmo, grid, picking, Maya-style navigation, rendering a shot). Each item becomes `root → body → inner(offset) → geometry/children`; the split matters: pivot maths reads *body* space, frozen transforms live on *inner*.
- `bEpicViewer_mixinPreviz.js` + `previzChannels` / `previzCurves` / `previzRender` / `previzUndo` — the panels and the edits (outliner, channel box, curve editor, render dialog, undo stack).
- three.js is **vendored in `vendor/three/`, deliberately outside `js/`**, so ComfyUI does not serve or import it at startup; it is fetched on demand through `/bepic/lib/three/<name>`.
- **Gaussian splats** (.spz, .splat, .ksplat, .sog, and a .ply whose vertices carry `scale_*` + `rot_*` — `isSplatPly`, ComfyUI's own rule) are drawn by Spark (`vendor/three/spark.module.js`, loaded with the first splat) as `SplatMesh` objects in the ordinary scene, turned 180° about X as ComfyUI's viewer turns them. One `SparkRenderer` per view (`_ensureSpark`, remade with the WebGL renderer). A splat has no geometry in three's sense, so a hidden `splatbounds` box beside it is what framing and picking measure. Server side, `model_writer` saves an in-memory `SPLAT` as .ply through core's `SplatToFile3D`, and never converts a splat to a mesh format (`is_splat_file`).

### Server side

- `viewer_api.py` — all `/bepic/*` routes, registered at import. Everything taking a path is filtered through `path_access.py`, which confines reads to ComfyUI's input/output/temp plus folders the user allows (`~/.bepic_viewer/roots.txt` — per OS user, NOT in ComfyUI's folder: a launcher's `git stash -u` there swept the old `bepic_viewer_roots.txt` away at every start; that file is still read and adopted — or `BEPIC_VIEWER_ROOTS`). Routes with side effects are POST only. `/bepic/roots` (the settings page's folder editor) is the one route that widens that list, so it is fenced by `path_access.may_edit`: same machine (loopback, or the server's own address), ComfyUI's own Origin, JSON POST; `BEPIC_VIEWER_ROOTS_REMOTE_EDIT=1` allows other machines, `BEPIC_VIEWER_ROOTS_LOCKED=1` none; the Host must be this machine's address or name (DNS rebinding). **A route that hands back a file's bytes serves media only** (`path_access.may_serve`: `MEDIA_EXTS`, which includes a glTF's `.bin` / `.mtl`): listing and writing need `is_allowed`, returning content needs `may_serve`. The list never holds a drive root, the home folder or above, a system folder or a hidden one (`too_broad`, enforced when read as well as when edited), and inside an added folder nothing below a dot folder or AppData is allowed. The Comfy registry's reviewer judges exactly this: versions were flagged `arbitrary-file-read`, `path-traversal`, `credential-exfiltration` (read the verdict in `status_reason.message`, `?include_status_reason=true`). **No route may start a process on the host** — the Explorer-opening routes were removed for exactly this reason, and the ComfyUI registry rejected the repo while they existed.
- `usd_io.py` / `abc_io.py` — USD stages and Alembic caches. The viewport speaks glTF only, so both are flattened server-side into a cached GLB "display proxy" and served through the ordinary file route. `abc_io.py` reads the Ogawa container itself (no Alembic bindings exist on PyPI); an Alembic cache is geometry per frame, so its proxy is keyed by `frame`.
- `color_io.py` — the viewer's colour transform: input colourspace → sRGB through OpenColorIO (`$OCIO`, else the built-in config; sRGB and Linear in numpy without it). The target is fixed (the config's sRGB output, the rule `bepic_templates`' colour node starts on); the input is picked in the viewer (`bEpicViewer_color.js`, the menu in the exposure bar) and travels as `cs=` on `/bepic/raw_view`, `/bepic/view_file` and `/bepic/thumb`. `media_resolve.proxy_for_colorspace` converts and caches one file per source and colourspace (JPEG, or PNG with alpha); without `cs` the older fixed proxy (`proxy_for_display`) still answers. The node therefore hands the viewer the saved EXRs themselves and writes no PNG copies. `buildImgUrl(obj, {noColor: true})` is for anything that is not the picture being looked at. A converted picture takes the **exposure** on the server too (`ev=`, a tenth of a stop per cache entry): input → working linear, multiply, → sRGB. `applyExposure`'s CSS brightness makes up only the stops the element on screen does not already carry (`el._bepicEv`, read off the loaded URL in `_setImgSrcCached`), which is all of them for a picture shown as it is and the live preview while a converted frame is on its way (`queueExposureReload`).
- `timeline_io.py` — the cut that lies beside a film, and the **Edit panel** (dock id `editTimeline`, the timeline button in the transport; `bEpicViewer_editTimeline.js`). A cut is an OpenTimelineIO file; one lies beside a film of the same name (`cut.mp4` / `cut.otio`; agentY's edit stage writes one, and so can Resolve or Premiere), one is started in the panel (New, or the first clips added). **Every open cut has a tab of its own** (key `edit:…`, no media frames, kept by the stale-tab sweep) **and plays there before anything is rendered** - see *Playing a cut* below. On a film with a cut beside it the timeline button lights up and opens that cut's tab; it is not opened by itself. The panel shows the cut of the tab that is up (`_editTlTab`; the others wait in `_editTlCuts`, all of them in localStorage `bepic.viewer.edits`, each with how it is looked at - zoom, track heights, solo - as `view`). **The three Edit panels - Edit, Inspector, Effects (`EDIT_PANELS`) - are up only while a cut's tab is**: `switchTab` hides them for any other tab (`editTlTabHidden`) and brings back the ones that were open (`_editTlWanted`, localStorage `bepic.viewer.editPanels`) with the next cut. The Edit panel is a column of track headers that stays and, beside it, a strip as wide as the zoom makes it (`view.zoom`, Ctrl+wheel about the pointer, the wheel or the middle button to pan): a ruler (drag to scrub), then the tracks top to bottom - texts, the higher video tracks, V1, A1, the sound tracks. A header carries the track's switch (off: saved, not rendered), its solo (`view.solo`, a way of looking: played, neither saved nor rendered - `liveTracks`) and, on its lower edge, its height. A clip is coloured by right-click or in the Inspector (`metadata.bepic.color` in the file). A dissolve is a bar over its join (`.edit-mix`, selection kind `mix`): its edges resize it, the Inspector has its length. A clip's body is dragged along its track or onto another one (`_editTlTrackUnder`, `transferClip`; a ghost shows where it would land): onto V1 it lies over what is there (an overwrite, `overwriteV1`; Ctrl+Shift: between the shots, an insert), onto any other track it is placed; off V1 it leaves a gap (`liftV1`). It is an editor: drag a shot's edge to trim, a shot to move, a text to move; drop rows of the file browser / history thumbs (the `application/x-bepic-history` payload) or a node dragged off the canvas (the page is watched for the release - LiteGraph keeps the pointer - and the node is put back) to add clips. **Tracks** (`cut.tracks`, `timeline_io.extra_tracks`): V1 is the cut itself - one shot after the other, dissolves, and GAPS (see *Modes, gaps, linked sound, snapping* below) - and A1 the bed under the whole film; every further track holds clips that are PLACED (`at`), and nothing moves when one does. A clip on a higher video track covers what is under it, **picture and sound** (the player has one element sounding at a time, and `timeline_render.covered` / `film_sound` follow the same rule so that the film is what was played); sound-track clips lie under everything. In the file they are OTIO tracks with gaps, the first audio track always being A1 (an empty one is written when a cut has sound tracks but no bed, or the first of them would be read back as the bed). Two clips of one track that share a moment: the later one is on top in the page, and on save the earlier ends where the later begins. An edit without a `tracks` / `off` key (an older page) leaves what the file holds of them alone. The numbers of the selection are in the **Inspector** and transitions, texts and plain colours in **Effects** (`bEpicViewer_editPanels.js`): the Inspector is in the viewer's own look (the panels' ground, the Parameters header, the Edit panel's buttons, cyan numbers - on purpose not any other program's; it was restyled once for looking like one) and holds the clip's name, tabs (Video / Audio / Timing / File; Title for a text, Transition for a dissolve), sections with a switch and a reset, a reset per row - and every row is something the preview plays and the render writes, no control that only looks like one. **A clip's transform, cropping and opacity** (`clip.fx`, `metadata.bepic.fx`; the table `FX` is in `timeline_io.py` and in the data module, and the two must agree): zoom, position and anchor point as fractions of the frame (y UP), rotation in degrees clockwise, a crop per side, opacity; `toff` / `coff` / `ooff` switch a section off and keep its numbers (`clipFx` is the effect as DRAWN, `rawFx` as its numbers stand). One arithmetic, twice: `fxPlace` gives the layer its CSS transform (put after the viewer's own) and a clip-path that is the frame taken back through that transform and cut to the crop; `timeline_render.lay` does the same with an affine transform and an alpha that is the picture's box less its crop - a change to one is a change to the other, and `fx_check`-style pixel tests of the render are cheap to rebuild. A clip on a higher track that no longer covers the frame has what is beneath it as `under` with `over: true` (`pictureAt`) and the player draws that ONE picture beneath, as it does for a dissolve; the render draws them all. A slider is live while dragged (`editPlayFxLive`, which changes no cut - a redraw would take the slider from under the pointer) and commits when let go. Not there, rather than there and dead: pitch and yaw, crop softness, dynamic zoom, speed, keyframes. An Effects item is dragged onto the timeline (`application/x-bepic-effect`) or double-clicked; a plain colour is a PNG the server makes (POST `/bepic/timeline_solid`, one file per colour and size), because a clip is a piece of a file; a text made here is a marker with no `ref`, drawn at once. Save (POST `/bepic/timeline`) writes the cut into the `.otio` and stamps it (`metadata.bepic.edited`); the film it lies beside is not touched. A tab closed with unsaved changes says so once and stays. **Render** (POST `/bepic/timeline_render`, `timeline_render.py`) makes the film of the saved cut in this process through PyAV - a ComfyUI dependency, so no program is started and the no-process rule holds: shots scaled to fit and padded, a dissolve blended frame by frame, the shots' own sound and the bed mixed in memory (hence `MAX_SECONDS`). It never writes over the film a cut lies beside (that may be somebody's render): the result lands by the export rule as the next version, with its own `.otio` marked `rendered`. **Texts are drawn** (`timeline_render.draw_texts`): each has a look of its own - `size` (percent of the picture's height), `x` / `y` (where its middle is), `color`, in the marker's `metadata.bepic`, with `timeline_io.TEXT_LOOK` where it says nothing - and the Edit tab writes the same texts over the picture while it plays (`_editPlayTitles`, a layer laid on the picture's rectangle; Arial in both, so they agree). The two must stay in step: a change to one is a change to the other. Texts switched off (`off.T`) are not drawn. `texts_left_out` stays in the answer, at 0. With no film, dropped clips start a new cut, saved by the export rule (kind `edit`). Rules worth knowing: the panel works on clips at FULL length with the dissolve leading into each (`timeline_io.editable`), OTIO lets clips meet mid-dissolve (`rebuild`) - a dissolve is split into whole frames that add up, or the film comes back a frame short; an existing clip is saved by `ref` (its place in the file) so everything another program wrote into it survives, a new one by `file`, which must pass `path_access.is_allowed`; a clip's length comes from POST `/bepic/timeline_probe` (PyAV reads the container header in this process - the server may not start a process to ask), and only where that fails from the browser (`<video>` metadata). `bEpicViewer_editTimelineData.js` is the arithmetic (pure, every edit returns a new cut; run it under node after a change).

- **Trimming like an editor; in and out** (`bEpicViewer_editTrim.js`, `EditTrimMixin`; arithmetic in the data module, tested in `tests/test_edit_timeline_trim.mjs`, the panel in `tests/test_edit_timeline_browser.py`). What a press on a clip does is decided by `_editTlEdgeAct` (where it lands, what is held) and shown BEFORE the press by `_editTlHover`: an editor's cursor (SVG data-URL cursors, `TRIM_CURSORS`), the side that will move lit (`.edit-trimhl`, `data-side`), and a tooltip with the edit point's timecode (`.edit-trimtip`, `D.timecode`, HH:MM:SS:FF). Within `EDGE_PX` of a block's edge: left of a V1 cut is the outgoing shot's OUT (`trimEnd`, ripple), right of it the incoming IN (`trimStart`, ripple); within `ROLL_PX` of the join (the middle zone - chosen over a modifier, so it needs no key) it is a ROLL (`rollEdit`: the cut moves, the film keeps its length; not on a join with a dissolve - there the dissolve's bar is on top: its edges change its length, its body rolls the cut under it, `_editTlMixRoll`). Modifiers: Alt on the body = SLIP (`slipClip`, in and out move together, the picture follows the pointer, held to the source, `.edit-slipband` shows where the source lies; `,` / `.` a frame, Shift a second - by `e.code`, so the layout does not matter); Alt+Shift on a V1 body = SLIDE (`slideClip`: the shot keeps its source and length and moves, the neighbour before ends later and the one after begins later in its source; refused at either end of the cut; on placed tracks a plain drag already moves a clip keeping its length); Alt on an edge = RETIME (`retimeClip`, "trim to fill": source in / out kept, `speed` = what fills the new length, 10 %..1000 %); Ctrl on the out-edge = LOOP EXTEND (`loopExtend`; Ctrl+L / Ctrl+Shift+L one more turn / ping-pong, `loopOnce`). Every trim knows where its source ends (`_editTlDur` from `/bepic/timeline_probe`, asked once per file in the background by `_editTlKnowFiles`): `outRoom` / `inRoom` hold trims, rolls and slides there; a still (`isStillImage`) has no source length, so it grows as far as it is pulled at either edge. Tracks: `lane` +n pictures, -1 the bed (A1), -2.. sound tracks. A film's sound on a track is the same asset with `srcEnable="audio"`, a muted picture `srcEnable="video"`. A loop is repeated clips (`_turns`), a ping-pong's way back a reversed `timeMap`; a still is `<video>`; texts are `marker`s (no look); embedded timecode goes into `start`. **Why absolute `file:///` URLs**: Apple's DTD says an asset's src is a "file: URL", and Resolve's manual (20, ch. 58) says it finds media by the embedded paths and otherwise asks for a folder, searching its subfolders; nothing found says it takes a relative one. **Not verified inside Resolve**: `srcEnable` and the 1.9 element order are from memory of later DTDs (the fetched one is 1.1); the free-version codec flags (`free_version_note`) are from third-party reports and warn only, nothing is transcoded. Do not start `Resolve.exe` to find anything out, not even with `--version`: it starts the program.
- **Several clips, takes, recreate** (`bEpicViewer_editTakes.js`, `EditTakesMixin`; arithmetic in the data module, tests `tests/test_edit_takes.mjs`, `tests/test_edit_takes.py`, `tests/test_edit_takes_browser.py`). Ctrl+click toggles a clip in the selection, Shift+click takes the range on one track; `_editTlSel` stays the last clip clicked and `_editTlMulti` ({list, sig}) is the list it belongs to - held to the cut by `selSignature` (counts and refs), so an edit that adds / removes / reorders clips, an undo or any other `_editTlSel` lets it go (`_editTlSelList` is the one reader). Outlined `.msel`; `viewerState().edit.selected` is the list `[{name, file, in, out, track, id}]` (id `V1:3` / `V2:0`, in/out of the source, 50 at most) plus `edit.otio`; text / dissolve selections stay one object as `edit.selected_item`. Right-click a clip: "Recreate with changes…" (dialog `.edit-recreate`, saves a dirty cut first, then `agentYViewerBridge.recreate({text, clips, otio})`), and "Takes" / "Retime to fit" for a clip with takes. **Takes**: `clip.takes = [{file, version, created, note, active, len?}]` (`metadata.bepic.takes` in the .otio, `timeline_io.clean_takes`; the active take's file is also the media reference's `target_url`, set through `may_use`); `addTake` / `switchTake` / `retimeToFit` in the data module and `timeline_io.add_take` do the same arithmetic. POST `/bepic/take` ({otio, takes:[{from_file, file, version, note}], retime}) writes the takes into the .otio (tmp + replace) and sends ComfyUI's `bepic.edit.take` ({otio, takes (with created), saved, retime}); each panel's `editTlTakeIn` applies it to every open cut that is that .otio or uses `from_file` as one undo step, and with `saved` to the saved baseline too (so the take is not an unsaved change). `bEpicSendToViewer` writes provenance (`provenance_write.py`: `<file>.agenty.json` key `provenance` + `<file>.prov.json.gz`, secrets redacted) so a shot can be made again.
- **Playing a cut** (`bEpicViewer_editPlay.js`, `EditPlayMixin`; what is on screen at a moment is `pictureAt(cut, t, live)` - the clip of the highest live video track, else the cut's own, else black - and what is heard under it `soundItems`): hooked in like previz, by a question asked first - `_editPlayOn` / `isEditTab()` - in `getImgCount`, `setFrame`, `play`, `stop` and `switchTab`, so the whole transport (scrub, step, loop, the ctrl-dragged range, the fps field) works on the film's frames. The clip at the frame is shown from its own file through the elements everything else already reads: a picture in `imgBase`, a film in `videoBase`. There are two `<video>`s taking turns - the one on screen IS `this.videoBase`, the other holds the next clip sought to its in point - and they change places at a cut, so a cut costs no loading; the viewer's own element is handed back in `editPlayLeave`. **A dissolve is played as one**: `pictureAt` gives the clip coming in and, as `under`, the one going out with `mix` (0..1); the outgoing clip keeps running in a second layer and the incoming one lies over it at that opacity, their volumes crossing the same way (`_editPlayUnder` / `_editPlayMix`). Which layers those are depends on what the clips are - the two `<video>`s, the `<img>`, and a second `<img>` (`_epImgB`) for picture into picture. `updateTransform` skips an unchanged transform, so every layer the player owns takes the viewer's zoom and pan from `_editPlayMirror` (called from `updateTransform` and after each show), not from being `videoBase` at the right moment. While playing, the film's clock is the clip's own `currentTime` (sound and picture cannot part); a still, and black, run on the wall clock; the bed and each sound-track clip are `<audio>` elements kept loosely beside it. `_videoOnTimeUpdate` / `_videoOnMeta` / `_videoOnEnded` stand down while it is on. `pictureAt` / `playAt` / `filmFrames` in the data module are its arithmetic.
- **Contact Sheet of 3+ history items** (`bEpicViewer_contactGrid.js`, `ContactGridMixin`; the layout maths `gridLayout` is pure, tested in `tests/test_contact_grid.mjs`, the browser side in `tests/test_contact_grid_browser.py`). Compare turned on (`toggleCompare`) with 2+ thumbnails Ctrl-selected compares THEM (`_tryEnterMultiCompare`): `_multiCompare = { key, snaps }` holds the snapshots in selection order (the selection Set's insertion order), the first two are pinned as the ordinary `historyCompare` pair, so every wipe works unchanged; Contact Sheet chosen with 3+ selected adopts them too. With 3+ the Contact Sheet is a grid of its own (`.contact-grid` in the viewport, the `grid-mode` class hides `#contact-container`), capped at `CONTACT_GRID_CAP` (16). While it is up (`_gridOn`) it owns the transport like the Edit tab does: `getImgCount` / `setFrame` / `play` / `stop` hand over to `_gridFrameCount` / `_gridSetFrame` / `_gridPlay` / `_gridStop`. One clock: the longest clip plays natively and is the master; every other `<video>` follows it on the same frame INDEX, corrected each animation frame by `followRate` (2 % steps - a rate change is not free) or a seek past 0.25 s; a shorter clip holds its last frame until the sheet loops. `_gridSync()` is the one place that turns it on/off and re-lays it; it runs from `toggleCompare`, `setSliderMode`, `exitHistoryCompare` and every compare-ticker frame (which also catches the paths that drop `historyCompare` directly). A pop-out pauses moved `<video>`s, hence `_gridAfterMove` from `_afterViewportMoved`. viewerState reports it as `compare.mode = "contact"` with `items`, `shown`, `indices`, `grid`; agentY's `[VIEWER]` line is just `compare=contact N items`.
- `file_writer.py` / `model_writer.py` / `previz.py` / `roto_raster.py` — saving frames in VFX formats, saving meshes, previz render folders, rasterising roto shapes.
- A MESH / 3D-file input to `bEpicSendToViewer` is saved in the 3D format picked in `file_format` (glb, gltf, obj, ply, stl, usd/usda/usdc — `model_writer.MODEL_FORMATS`, appended after the image and video formats): `model_writer.convert` reads it with trimesh (USD through `usd_io.display_proxy`) and writes it, USD by its own pxr writer. An image or video format on a 3D input keeps the input's own format; a 3D format on an image falls back to png. FBX has no writer here.
- `nodes.py` — `bEpicSendToViewer`, `bEpicImageViewerRoto`, `bEpicImageViewerSAM3Collector`, `bEpicScene3D`. Node → viewer is a `bepic.viewer.update` websocket message; the nodes also return a `ui` dict so their files appear in ComfyUI's history and Assets panel (the frontend suppresses the inline node preview instead of the node withholding `ui`).

## Import and export: one vocabulary, one set of rules

The viewer's ways in and out grew one feature at a time and were then brought under one rule. New work follows it.

**Four words, and they do not overlap.** *Open* shows a file in the viewer. *Add* brings a file into what is being worked on (a scene, a cut). *Save* keeps the working document (a scene, a cut) where it already lives. *Export* writes a deliverable (a film, frames, a USD stage, a PNG). "Render" is the button inside an export dialog, not a fifth idea. No "Import", "Load" or "Download" in new UI.

**`export_rules.py` decides, for every export:**
- *what a format is* (`VIDEO`, `video_settings`): a container means the same codec wherever it is offered. MOV is ProRes 422 unless H.264 is asked for; MP4 is H.264; WebM is VP9. Quality is `high` / `medium` / `low`, and each encoder's number for those is there and nowhere else. `/bepic/export_options` serves the table to the page.
- *where a file goes and what it is called* (`target`): with a sequence and shot (a context node on the canvas, sent by the page as `context`) the bEpic layout, `<Seq>/<Shot>/<kind>/v###/<shot>_v###_<name>.<ext>`; without, `bepic/<kind>/<name>_v###.<ext>`. Under ComfyUI's output folder, always the next version - an export never writes over an earlier one. `/bepic/export_target` previews it without creating anything.

**The shared pieces** (`bEpicViewer_exportUI.js`, plain functions): `openExportDialog` (name, format, codec, quality, the feature's own rows, and "Goes to" - the path asked from the server before anything is written), `openFilePicker` (the file browser's listing as a question: `/bepic/browse` again, so the same folders and refusals; it opens where the kind is kept, `/bepic/export_places`, and remembers the folder per `id`), `notice` (a toast; there is no `alert()` and no `prompt()` for a path anywhere), `canvasContext` (the sequence and shot the graph names). `sequence_target` / `sequence_frame` are the rule for numbered frames: in a shot they lie in the version's folder, without one in a folder of their own name.

**Where each feature stands** - all of them follow the rule:
- *Edit panel*: Export… renders by the rule; a new cut is saved by it. Export to Resolve… lands beside the cut, as a folder, and takes the next version too.
- *Annotations*: versioned, in the shot's folder when there is one.
- *Previz*: Save scene, Export USD (dialog, versioned), Open scene, Open USD / Alembic (picker). The render lands by the rule too: frames are uploaded into `output/previz/<name>/` (the take's working folder), then encoded to the next version, or - kept as stills - moved (`/bepic/previz_publish`). `output/previz/<name>.latest.json` (`previz.note_render` / `latest_render`) says where the take went, which is how the scene node still finds it by `render_name`; a new take removes the note, never the earlier version. Takes and scenes from before the rule (`output/previz/<name>.mp4`, `output/3d_scenes`) are still read, and the picker offers the old folder.
- *What is on screen* (`bEpicViewer_exportView.js`, `export_view.py`, POST `/bepic/export_view`; the Export Frame or Clip command - it has a hotkey and no button): the current frame as a PNG, or the whole clip / sequence as a film - those two and no more. A picture is exported as shown (through the colourspace picked, without exposure); a video is a one-clip cut through `timeline_render`, so it keeps its sound. On a 3D scene it opens the previz render dialog, on an Edit tab the cut's export.
- *A frame dragged off the timeline* goes to `<kind folder>/frames/`, named after its clip and frame and so not versioned: the same frame twice is the same file.
- *Send to Viewer*: a `codec` widget, **last** among its inputs (saved workflows hold widget values by position - anything new goes after it), shown for `mov`; `auto` is the rule's default, so a MOV from the node is ProRes now unless H.264 is picked.

**A film a `<video>` cannot play** (ProRes; 10-bit or 4:2:2 H.264) is shown through an H.264 copy made on first request and cached in temp (`media_resolve.video_proxy`, called from `_file_response`). Only what is looked at goes through it: exports, cuts and extracted frames read the film itself.

**In and out of a panel are buttons at the top left of its body**, at the Outliner's size (`.previz-btn.previz-icon`), in one order: New, Add (Lucide's circle-plus, `icon-circle-plus`), then what the panel has of its own, then Save / Export (`icon-save`, a menu). Outliner: New · Add · Edit · Save/Export/Render. Edit panel: New · Add (files, canvas nodes, a new track) · Save/Export, and no second Save at the right. They were once two small glyphs in the title bar and were overlooked there; a title bar holds a name and a close button, nothing else. A panel that takes files takes the same drop - the `application/x-bepic-history` payload - as the Edit panel and the viewport (`previzAddDropped` for the Outliner; on an Edit tab the viewport adds clips).

**Dock panels as tabs** (`bEpicViewer_mixinDock.js`): a panel dropped onto the MIDDLE of another (the outer thirds still mean before / after) shares its place - two more fields on a layout entry, `tab` (the group's name) and `behind` (every member but the one in front). A panel that is behind is open (`isPanelDocked`) but not drawn (`isPanelFront`); the front panel's title bar names them all, and a press on a name brings that one up (`dockTabFront`, which also fires `_onPanelShown`). Anything that toggles a panel should bring a behind one to the front rather than close it (the bar's groups do). `dockPanelTo` takes a panel out of its group; members stay next to each other in the rail's list (`_dockRegroup`).

**The lower bar** (`bEpicViewer_barGroups.js`): playback at the left; then the panels in three groups, each one button that opens a short menu upwards - ComfyUI (its own logo, from the frontend's `/assets/images/`): History, Parameters · 3D (Lucide `box`): Outliner, Channel Box, Curve Editor (the panel once called Animation Curves; its home is the bottom rail), on a 3D tab · Timeline: Edit, Effects, Inspector; everything else (layout, shape overlay, page dock, files, run, clear) at the right end. It is done with CSS `order` and a spacer: no button is re-parented, the old History / Parameters buttons stay in the DOM hidden and still carry the handlers and the lit state. A new panel goes into a group, not onto the bar.

**Where an export ends up on screen**: `exportLanded(paths)` puts it in the History of one tab, "Exports" (`folder_exports`), newest first, without switching to it. The Edit panel's film still opens in a tab of its own, beside the cut's, and an annotation joins the History of the tab it was drawn on.

**Kept on purpose:** the old routes' behaviour without `rule: true` (an older cached page, agentY) - new behaviour is asked for by that flag or a new route, never by changing what an existing request does.

### Worlds (branch `worlds`)

Walkable worlds built from reference images. The viewer only *shows* them; they are *made* by a separate repo,
`ComfyUI-bEpicWorlds` (sibling folder in custom_nodes; library, nodes, `/bepic_worlds/*` routes, MCP server, CLI).
The contract is the scene schema — `SCHEMA.md` there, `bEpicViewer_worldData.js` here.

- `bEpicViewer_worldData.js` — the world item kinds (environment, terrain, scatter, depthmesh), camera `reference`,
  scene `walk` / `world`, as pure data; `parseScene` reads them through it.
- `bEpicViewer_world3d.js` — a mixin on Model3DView (installed with `defineProperties`: it has a getter): sky/sun/fog
  replacing the studio rig, terrain, instanced scatter with wind, depth mesh, walking, reference overlay, feedback pins.
  World items rebuild when `_worldKey` (their settings as JSON) changes.
- `bEpicViewer_previzWorld.js` — the panel side: Add → World, channel-box rows from `WORLD_FIELDS`, Walk/Note buttons,
  notes POSTed to `/bepic_worlds/feedback` (kept in the scene only when that route is missing).
- A world arrives as a normal `bepic.viewer.update` with `scene_replace` (replace the tab's scene), `tab_label` and
  `focus_tab`; tab keys start `world:` and survive the stale-tab sweep.
- A world built around a whole-picture model has it as an ordinary `model` item with id `scene` (placed by the pack's
  `set_scene_model`), so the World tab is the only 3D view. An HDR sky (`sky.hdr`, `.hdr`/`.exr`) is read by the
  vendored `HDRLoader` / `EXRLoader` from `/bepic/view_file?…&raw=1` (`raw` skips the PNG display proxy, which would
  clip it); with `sky.lighting` it is also the world's PMREM environment, and `render.reflections: "sky"` keeps the
  cube capture from replacing it (`_worldSkyLight` / `_worldDropSkyLight`).

### Keys and curves (previz and roto)

- One key bar in the transport (Set Key, Delete Key, Autokey, ease menu), built in `previzEnsureKeyBar`; `_keyBarContext()` decides whether a press keys the previz scene or the roto tool's shapes, and `keyBarSync()` shows it for whichever is up.
- The drawing tools' options (Roto, SAM3 points/boxes, Annotate) live in the **Parameters** panel: while a tool is on, `_toolShowDock` puts it in `tool-mode` (header names the tool, lock hidden, node widgets hidden, the selection monitor paused via `_paramsToolMode`) and each tool fills `this._toolPanel`, a sibling of `#params-content`. The panel opens with the tool, closes after it only if it was closed before, and goes back to the node on 3D tabs. Nothing floats over the picture but the toolbar.
- Roto and SAM3 follow the canvas selection: selecting a Roto / SAM3 Collector node brings its tool up, selecting anything else puts a tool brought up that way away again (`_toolFollowSelection`, called from the params monitor's tick; the params lock holds it). Their toolbar buttons only create a node (`createToolNode`, left selected) — the selection does the rest. Annotate has no node and still toggles.
- Two dock panels, one look: previz's **Animation Curves** (`bEpicViewer_previzCurves.js`, value graphs) and **Roto Curves** (`bEpicViewer_rotoCurves.js`, a shape's timing between keys). Both are built from `bEpicViewer_curveUI.js` (panel skeleton, list/graph splitter, tangent arms), which stays plain functions so the two mixins can't collide.
- **Node parameters** can be keyed too, on nodes that declare an optional `animation` STRING input whose spec lists `bepic_animatable` names (the bEpic image nodes in `bepic_templates`: Transform, Grade, ColorCorrect, Blur, Merge, Constant, Crop, Retime). The keys are JSON in that hidden widget — a real input, so a changed curve re-runs the node. `bEpicViewer_paramAnimData.js` is the format and the maths (pure); `bepic_templates/bepic_anim.py` renders it and **must interpolate identically** (compare the two on random tracks after any change). `bEpicViewer_paramAnim.js` puts key toggles on the Parameters rows (Nuke rules: an animated value keys itself when edited; Alt-click drops a track, leaving the widget at the frame's value), and makes the key bar's third context, `params`; `bEpicViewer_paramCurves.js` is the **Parameter Curves** panel (dock id `paramCurves`, opened by ∿ in the Parameters header).
- A roto key's `tangents[frame]` carries `{ox, oy, ix, iy, hold}`; `roto_raster.py` must interpolate exactly as `_rotoSegEase` does, or the mask a node renders won't match the viewer.
- Each roto shape has a `mode` (union, plus, minus, intersection, xor — the bEpic Nuke ChannelMerge operations, shape = A, the shapes before it in the list = B, clamped after each). `roto_raster.MODES` / `_merge` and the viewer's `ROTO_MODES` / `rotoMerge` must stay identical. Intersection is the one mode that changes pixels outside a shape's region (to 0), so the renderer handles it on the whole frame. The viewer's mask preview composites the same way on a canvas (`_rotoRenderComposite`), sized to the viewport — not to `#bepic-tool-draw`, which keeps its default 300x150 box and draws the rest as overflow.
- The Roto toolbar button binds to a selected Roto node instead of creating one (`selectedToolNode`); the Roto Curves panel opens only from its button.
- `roto_raster.rasterize` stays fast by working each layer only inside the box its outline + feather/dilate/blur can reach, reusing the mask of any frame whose outlines equal an earlier one's, and rendering the rest on a thread pool (`BEPIC_ROTO_THREADS` caps it). A change to the matte maths must keep the box margin wide enough (3σ per blur, the dilate radius) or it clips; compare its output against the old renderer's pixel for pixel.
- Anything that moves the frame must call `_toolsFrameChanged()` (image sequences in `setFrame`, videos in its video branch and `_videoOnTimeUpdate`), or the roto overlay lags until the next unrelated redraw.

### Hotkeys

`bEpicViewer_keymap.js` is the single table feeding three consumers: ComfyUI's command list (so every action is rebindable in Settings → Keybinding), the panel's own key handler (which answers while the viewer is hovered), and the in-viewer help overlay. Add actions there, not ad-hoc listeners. A combo ComfyUI already owns ships unregistered and still works while hovered.

## Publishing

`.github/workflows/publish.yml` publishes to the Comfy registry **on any push to `master` that touches `pyproject.toml`**, and only from `szprivate/ComfyUI-ImageViewer`. So: bumping `version` in `pyproject.toml` *is* publishing. Push other changes freely; touch that file only when a release is intended.

Remotes: `origin` = szprivate (dev, and the one that publishes). There used to be a second remote for bEpic-studio (the org); check `git remote -v` before pushing.
